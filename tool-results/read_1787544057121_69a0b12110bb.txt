    72→## 1. Addition / Subtraction Game
    73→
    74→**Files:** `addition_subtraction_game.php`, `addition_subtraction_setup.php`
    75→
    76→### Settings (URL query params on game.php)
    77→| Param | Type | Range / Values | Default |
    78→|---|---|---|---|
    79→| `solvingMethod` | string | `direct` / `friendsOf5` / `friendsOf10` | `direct` |
    80→| `numberLength` | int | 1–4 (1=آحاد, 4=آلاف) | 1 |
    81→| `termsCount` | int | 2–20 (sequential) / 2–10 (full) | 2 |
    82→| `displayTime` | float | 0.1s–10s, step 0.1 | 1.5s |
    83→| `disappearTime` | float | 0.1s–10s, step 0.1 | 0.5s |
    84→| `displayMethod` | string | `sequential` (flash) / `full` (whole problem visible) | `sequential` |
    85→
    86→Note: `displayTime` and `disappearTime` are passed in seconds in the URL; PHP multiplies by 1000 (`floatval(...) * 1000`) before storing them in `settings_json` as ms. The JS re-reads them from `URLSearchParams` and again multiplies by 1000 — so the URL is in seconds, the JSON is in ms.
    87→
    88→> ⚠️ `solvingMethod` is captured by PHP into `settings_json` but **never used** in JS question generation. `friendsOf5` / `friendsOf10` abacus-style carry/borrow constraints are only honored in the legacy `exam-generator.php` (PHP) — not in any of the live games. This is a dead feature flag in the new games.
    89→
    90→### Question generation (JS, `generateQuestion()` in addition_subtraction_game.php ~ line 391)
    91→```js
    92→const max = Math.pow(10, numberLength);
    93→let currentTotal = Math.floor(Math.random() * max);    // seed with first term
    94→const terms = [currentTotal];
    95→for (let i = 1; i < termsCount; i++) {
    96→    let op = Math.random() > 0.5 ? '+' : '-';
    97→    let num = Math.floor(Math.random() * max);
    98→    if (op === '+' && currentTotal + num < 10000000) { terms.push('+', num); currentTotal += num; }
    99→    else if (op === '-' && currentTotal - num >= 0)   { terms.push('-', num); currentTotal -= num; }
   100→    else { terms.push('+', 0); }   // fallback (zero term) when constraints fail
   101→}
   102→// terms: [n0, '+', n1, '-', n2, ...]; answer = currentTotal
   103→```
   104→- **Cap:** total running sum cannot exceed 10,000,000; subtraction never goes negative (mid-term guard).
   105→- Terms are interleaved `[num, op, num, op, num, ...]`.
   106→
   107→### Game flow
   108→1. `startCountdown()` — 3·2·1·0 overlay, then `startGame()`.
   109→2. `nextQuestion()` — increments `questionCount`, generates a question, clears input, branches on `displayMethod`.
   110→3. **`sequential`** (`displayQuestionSequentially`): shows each term one at a time for `displayTime` ms, then a `disappearTime` ms blank gap; after all terms, displays a yellow "?" and enables input.
   111→4. **`full`** (`displayFullQuestionVertical`): renders the whole vertical-math block immediately and enables input. Subtraction rows are styled in red.
   112→5. **Answer entry** — readonly `<input>` updated by an on-screen 12-button keypad (1–9, ⌫, 0, ✓). Keyboard 0–9, Backspace, Enter also work via a global `keydown` listener. `addNum / deleteLastDigit / submitAnswer` short-circuit when `!isAnswering`.
   113→6. `checkAnswer(userVal)` — `isCorrect = (userVal === currentQuestion.answer)`; pushes a row into `gameResults[]`:
   114→   ```js
   115→   { question, userAnswer, correctAnswer, isCorrect, timeTaken: timeTaken.toFixed(2) }
   116→   ```
   117→   Bumps `liveScore` on success. Waits 1 s, then calls `nextQuestion()` again. **No fixed question count** — the game runs indefinitely until the user presses the stop button.
   118→7. `endGame(save)` — `Swal.fire` dialog: "حفظ وخروج" (save & exit) or "تحميل تقرير PDF".
   119→   - Save: `fetch('', { method:'POST', body: new URLSearchParams({results_json: JSON.stringify(gameResults)}) })` then redirect to setup.
   120→   - PDF: hidden `#resultsContainer` HTML table is rendered via `html2canvas(scale:2)` and embedded into a `jsPDF` A4 page, saved as `Training_Report_<student>_<YYYY-MM-DD>.pdf`. The PDF container also attempts to save the results first.
   121→
   122→### DB writes
   123→- POST endpoint: `addition_subtraction_game.php` with form body `results_json=<JSON>`.
   124→- Calls `saveTrainingResults($pdo, $user_id, 'addition_subtraction', json_encode($settings), $results_json)` (see `game_functions.php`).

   175→### Question generation (JS, `generateQuestion()` line 285)
   176→Algorithm inverts the division to guarantee integer quotients:
   177→```js
   178→// 1) Build divisor d in [10^(len_d-1), 10^len_d - 1]; for 1-digit, force d >= 2
   179→let d = Math.floor(Math.random() * (max_d - min_d + 1)) + min_d;
   180→if (len_d === 1 && d < 2) d = Math.floor(Math.random() * 8) + 2;
   181→
   182→// 2) Compute allowed quotient range so the dividend keeps the requested digit count
   183→const min_D = 10 ** (lenD - 1);
   184→const max_D = 10 ** lenD - 1;
   185→const min_q = Math.ceil(min_D / d);
   186→const max_q = Math.floor(max_D / d);
   187→
   188→// 3) Fallback when settings are impossible (e.g. 2-digit dividend / 3-digit divisor)
   189→if (min_q > max_q) return { n1:100, n2:2, answer:50, text:"100 ÷ 2" };
   190→
   191→// 4) Random quotient, derive dividend
   192→const q = Math.floor(Math.random() * (max_q - min_q + 1)) + min_q;
   193→const D = q * d;
   194→return { n1: D, n2: d, answer: q, text: `${D} ÷ ${d}` };
   195→```
   196→- Display theme is cyan/blue (`#06b6d4`, `#2563eb`).
   197→- Otherwise the runtime (countdown, keypad, timer, save, PDF) is identical.
   198→
   199→Game type saved: `'division'`.

   203→## 4. Abacus Game (no DB persistence)
   204→
   205→**Files:** `abacus_game.php`, `abacus_setup.php`
   206→
   207→### Settings
   208→| Param | Type | Range | Default |
   209→|---|---|---|---|
   210→| `rods` | int | 3–13 (clamped in PHP) | 5 |
   211→| `theme` | string | `wood` / `neon` / `candy` / `gold` / `glass` | `wood` |
   212→| `mode`  | string | `free` / `challenge` | `free` |
   213→
   214→### Anatomy
   215→- A frame with N vertical rods.
   216→- Each rod has **1 heaven bead** (`data-val="5"`) above the beam and **4 earth beads** (`data-index="0..3"`, each value 1) below.
   217→- A `<div class="rod-val">0</div>` per rod shows the digit (only in `free` mode; hidden in `challenge`).
   218→
   219→### Value computation (`updateValues()`)
   220→```js
   221→rods.forEach((rod, index) => {
   222→    let rodVal = 0;
   223→    if (rod.querySelector('.heaven').classList.contains('active')) rodVal += 5;
   224→    rodVal += rod.querySelectorAll('.earth.active').length;  // each active earth bead = 1
   225→    rod.querySelector('.rod-val').innerText = rodVal;
   226→    const power = (rods.length - 1) - index;   // leftmost rod = highest power of 10
   227→    grandTotal += rodVal * Math.pow(10, power);
   228→});
   229→```
   230→
   231→### Modes
   232→1. **Free mode** — drag (touch or mouse) or click beads to toggle them; live grand-total displayed at the top; "تصفير" (reset) button at the bottom. Bead direction logic:
   233→   - Heaven bead: drag **down** activates (value 5 added), drag **up** deactivates.
   234→   - Earth beads: dragging **up** activates the bottom-most N beads up to the touched one (they bunch upward against the beam); dragging **down** deactivates from the touched index upward.
   235→   - Activation cascades: clicking bead #2 activates beads 0–2; clicking bead #2 again deactivates beads 2+ (PHP confirms via `for (let i = 0; i <= index; i++)`).
   236→   - Threshold of 10 px of vertical drag triggers the toggle.
   237→2. **Challenge mode** — beads are NOT interactive. `newChallenge()`:
   238→   - Generates `currentTarget = Math.floor(Math.random() * (max * 0.9)) + 5` where `max = Math.pow(10, min(rodsCount, 6)) - 1`.
   239→   - Calls `setAbacusValue(currentTarget)` to programmatically position beads.
   240→   - Builds 4 multiple-choice options: the correct value plus 3 random offsets in `[-5, +5]` (excludes 0 to avoid a duplicate).
   241→   - On click, `checkAnswer(selectedVal)` shows a SweetAlert2 success (1 s) and then `newChallenge()` again. **No persistent score, no DB write.**
   242→
   243→### Misc
   244→- A 4-bead-per-rod base64-encoded WAV click sound is embedded via `new Audio('data:audio/wav;base64,UklGRigAAABXQVZFZm10IBAAAAABAAEAQB8AAEAfAAABAAgAZGF0YQQAAAAAAA==')`.
   245→- Bead width is dynamic CSS: `--bead-w: calc(min(10vmin, (90vw / rods) - 1vmin))`.
   246→- `abacus_game.php` does **NOT** call `saveTrainingResults` — there is no `trainings` row written for abacus sessions. Pure client-only module.

   408→## 9. exam/generate-exam.php — the modern exam wizard
   409→
   410→> **Important:** Despite the file name and the prompt mentioning "AI/OpenAI API", this file does **NOT** call any AI/OpenAI API. This is significant for the Next.js rebuild — the z-ai-web-dev-sdk LLM can be introduced later for richer question text, but currently the platform is fully deterministic.
   411→
   412→### Endpoints
   413→1. **GET `/exam/generate-exam.php`** — renders the 5-step wizard UI (Bootstrap 5, jsPDF, jspdf-autotable).
   414→2. **POST `/exam/generate-exam.php`** with header `X-Action: save_exam` and JSON body →

   427→
   428→### Wizard steps
   429→| # | Name | Fields |
   430→|---|---|---|
   431→| 0 | General | `examTitle` (ASCII only, validated by regex `[A-Za-z0-9\s]+`), `columnsCount` (5 or 10) |
   432→| 1 | Add/Sub | `as_questionsCount` (0 or ≥5, max 100), `as_numberLength` (1–5), `as_termsCount` (2–10), `solvingMethod` (`direct | friendsOf5 | friendsOf10 | friendsOf5And10`) |
   433→| 2 | Multiply | `mul_questionsCount`, `mul_num1Length` (1–3), `mul_num2Length` (1–2) |
   434→| 3 | Divide | `div_questionsCount`, `div_dividendLength` (2–4), `div_divisorLength` (1–4), `div_decimalOption` (`integers | decimals`) |
   435→| 4 | Imagination | `im_questionsCount`, `im_numberLength`, `im_termsCount`, `im_solvingMethod` (same options as as) |
   436→
   437→The user can **skip** any step 1–4; skipped steps set their count to 0 and visually mark the nav indicator red.
   438→
   439→### Question-generation (JS, executed client-side)
   440→```js
   441→function generateAddSubQuestion(s) {
   442→    const terms = []; let v = 0;
   443→    for (let i = 0; i < s.as_termsCount; i++) {
   444→        const num = Math.floor(Math.random() * (Math.pow(10, s.as_numberLength) - 1)) + 1;
   445→        terms.push(num); v += num;
   446→    }
   447→    return { type:'add_sub', terms, answer: v };
   448→}
   449→// generateImaginationQuestion is identical but uses im_* settings.
   450→
   451→function generateMultiplyQuestion(s) {
   452→    const num1 = Math.floor(Math.random() * (Math.pow(10, s.mul_num1Length) - 1)) + 1;
   453→    const num2 = Math.floor(Math.random() * (Math.pow(10, s.mul_num2Length) - 1)) + 1;
   454→    return { type:'multiply', text:`${num1} × ${num2}`, answer: num1*num2, terms:[] };
   455→}
   456→
   457→function generateDivideQuestion(s) {
   458→    if (s.div_decimalOption === 'integers') {
   459→        let dividend, divisor, quotient, attempts = 0;
   460→        do {
   461→            quotient = Math.floor(Math.random() * 90) + 10;          // 10–99
   462→            const minDiv = 10 ** (s.div_divisorLength - 1);
   463→            const maxDiv = 10 **  s.div_divisorLength     - 1;
   464→            divisor  = Math.floor(Math.random() * (maxDiv - minDiv + 1)) + minDiv;
   465→            dividend = divisor * quotient;
   466→            if (++attempts > 200) return { type:'divide', text:`120 ÷ 10`, answer:12, terms:[] }; // failsafe
   467→        } while (String(dividend).length !== s.div_dividendLength);
   468→        return { type:'divide', text:`${dividend} ÷ ${divisor}`, answer:quotient, terms:[] };
   469→    } else { // decimals
   470→        // dividend and divisor in their requested ranges, quotient = (dividend/divisor) rounded to 1 or 2 dp (70% chance of 1 dp)
   471→        const decimalPlaces = Math.random() < 0.7 ? 1 : 2;
   472→        const quotient = parseFloat((dividend / divisor).toFixed(decimalPlaces));
   473→        return { type:'divide', text:`${dividend} ÷ ${divisor}`, answer:quotient, terms:[] };
   474→    }
   475→}
   476→```
   477→
   478→### Validation rules
   479→- Each section requires 0 questions (skip) or ≥ 5 (otherwise error).
   480→- Total `questionsCount` must be > 0.
   481→- Integer division with the chosen lengths must be mathematically feasible (validated against `minPossibleDividend` / `maxPossibleDividend` for a 2-digit quotient).
   482→
   483→### PDF generation (client-side, `createPdfDoc()`)
   484→- Uses **jsPDF + jspdf-autotable**.
   485→- Header box: title centered, "Name:", "Date:", "Time:", "Score: ___ / N".
   486→- Body grouped by operation type, ordered: `add_sub → multiply → divide → imagination` (imagination always last).
   487→- Vertical questions (add/sub/imagination): rendered as multi-row `autoTable` tables, one column per question, head row = question numbers, body rows = term values; trailing blank row for student's answer.
   488→- Horizontal questions (multiply/divide): 2 questions per row, each formatted `(N) <question> = ` for the exam or `(N) <answer>` for the answer key.
   489→- Final page is an **"Answer Key"** rendering the same grouped questions with the answers in place of blanks.
   490→- A faint diagonal **watermark** with the logged-in `username` is applied to every page (opacity 0.4, 60 pt font, 45° angle).
   491→
   492→### Preview/download flow
   493→1. Wizard → `submit` event → builds `settings` object → `generateAllQuestions(settings)` → stores `currentExamData = { settings, questions }`.
   494→2. Hides the wizard, shows a success screen with "معاينة وتحميل" (preview) and "إنشاء امتحان جديد" (reload) buttons.
   495→3. Preview: `generatePreview()` calls `createPdfDoc()`, outputs to a data URI, and sets `<iframe id="pdfPreviewFrame">` src.
   496→4. Confirm & download: POSTs the JSON `settings` to the same URL with `X-Action: save_exam`; on success calls `currentExamDoc.save(<title>_<date>.pdf)`.

   527→## 11. exam-generator.php — legacy v2.0 generator (server-side)
   528→
   529→This is an older, standalone PHP route that overlaps with `exam/generate-exam.php`. It does server-side question generation (PHP `rand()`) and saves to `trainings` (not `generated_exams`).
   530→
   531→### Endpoint
   532→- `GET /exam-generator.php` — renders form + (if previous POST) the generated exam sheet and answer key.
   533→- `POST /exam-generator.php` with the form fields below → generates questions, persists to DB, re-renders.
   534→
   535→### Settings (defaults)
   536→```php
   537→$defaults = [
   538→    'count' => 20,
   539→    'operation' => 'mixed',         // mixed|add|subtract|multiply|divide
   540→    'range_min' => 1,
   541→    'range_max' => 100,
   542→    'mode' => 'direct',             // direct|friends_5|friends_10
   543→    'no_negative' => true,
   544→    'integer_division' => true,
   545→    'no_duplicates' => true,
   546→    'shuffle' => true,
   547→    'seed' => '',
   548→];
   549→```
   550→
   551→### Generation functions (PHP)
   552→```php
   553→function generateAddition(int $min, int $max, string $mode): array {
   554→    [$op1, $op2] = [rand($min,$max), rand($min,$max)];
   555→    $isValid = match($mode) {
   556→        'friends_5'  => ($op1 % 10) % 5 + ($op2 % 10) % 5 >= 5,    // carry through 5
   557→        'friends_10' => ($op1 % 10) + ($op2 % 10) >= 10,           // carry through 10
   558→        default      => true,
   559→    };
   560→    return $isValid ? ['op1'=>$op1,'op2'=>$op2,'operator'=>'+','result'=>$op1+$op2] : [];
   561→}
   562→
   563→function generateSubtraction(int $min, int $max, string $mode, bool $noNegative): array {
   564→    [$op1,$op2] = [rand($min,$max), rand($min,$max)];
   565→    if ($noNegative && $op1 < $op2) [$op1,$op2] = [$op2,$op1];   // swap to avoid negatives
   566→    $isValid = match($mode) {
   567→        'friends_5'  => ($op1 % 10) % 5 < ($op2 % 10) % 5,        // borrow from 5
   568→        'friends_10' => ($op1 % 10) < ($op2 % 10),               // borrow from 10
   569→        default      => true,
   570→    };
   571→    return $isValid ? ['op1'=>$op1,'op2'=>$op2,'operator'=>'-','result'=>$op1-$op2] : [];
   572→}
   573→
   574→function generateMultiplication(int $min, int $max): array {
   575→    $m_max = $max > 20 ? 20 : $max;     // capped to 20 to keep products reasonable
   576→    $m_min = $min > 10 ? 1  : $min;
   577→    $op1 = rand($m_min, $m_max); $op2 = rand($m_min, $m_max);
   578→    return ['op1'=>$op1,'op2'=>$op2,'operator'=>'*','result'=>$op1*$op2];
   579→}
   580→
   581→function generateDivision(int $min, int $max): array {
   582→    $op2 = rand(max(2,$min), $max>20?20:$max);
   583→    if ($op2 == 0) $op2 = 1;
   584→    $result = rand($min, max($min, floor($max/$op2)));
   585→    $op1 = $op2 * $result;
   586→    return ['op1'=>$op1,'op2'=>$op2,'operator'=>'/','result'=>$result];
   587→}
   588→```
   589→
   590→### Generator loop
   591→- Picks random ops from `$operations_pool` (mixed pool `['+','-','*','/']` or single op based on `operation`).
   592→- `no_duplicates` builds a key from sorted operands (`min . op . max` for `+`/`*` to dedupe commutatively).
   593→- `max_attempts = count * 20` to prevent infinite loops.
   594→- `shuffle` randomises final order.
   595→- Optional numeric `seed` calls `srand((int)$seed)` for reproducible exams.
   596→
   597→### DB write
   598→```php
   599→$sql = "INSERT INTO trainings (user_id, game_type, settings_json, results_json, performance_notes) 
   600→        VALUES (?, ?, ?, ?, ?)";
   601→$stmt = $pdo->prepare($sql);
   602→$stmt->execute([
   603→    $_SESSION['user_id'],
   604→    'math_exam_generator',
   605→    json_encode($options),
   606→    json_encode($questions),
   607→    'تم توليد امتحان رياضيات بنجاح.',
   608→]);
   609→```
   610→Note this is the **only** place where `solvingMethod` (via `mode = friends_5 / friends_10`) is actually honoured for question filtering.

   613→- Plain HTML/CSS, no Bootstrap, prints with `window.print()`. Two-column exam sheet + 3-column answer key on a single scrollable page.

   617→## 12. `saveTrainingResults()` (game_functions.php) — the shared persistence layer
   618→
   619→```php
   620→function saveTrainingResults(PDO $pdo, int $user_id, string $game_type, string $settings_json, string $results_json): bool {
   621→    $results = json_decode($results_json, true);
   622→    // Compute aggregates
   623→    $correct_count = 0; $total_time = 0; $total_questions = count($results);
   624→    foreach ($results as $r) {
   625→        if (!empty($r['isCorrect'])) $correct_count++;
   626→        if (isset($r['timeTaken']))  $total_time += (float)$r['timeTaken'];
   627→    }
   628→    $total_score  = $correct_count;                                  // 1 point per correct
   629→    $average_score = ($total_questions > 0) ? ($correct_count / $total_questions) * 100 : 0;
   630→    $avg_time_per_question = ($total_questions > 0) ? $total_time / $total_questions : 0;
   631→    $performance_notes = "متوسط وقت الإجابة: " . number_format($avg_time_per_question, 2) . " ثانية.";
   632→
   633→    $sql = "INSERT INTO trainings 
   634→            (user_id, game_type, settings_json, results_json, total_score, average_score, performance_notes) 
   635→            VALUES (:user_id, :game_type, :settings_json, :results_json, :total_score, :average_score, :performance_notes)";
   636→    $pdo->beginTransaction();
   637→    $stmt = $pdo->prepare($sql);
   638→    $stmt->execute([...]);
   639→    if ($stmt->rowCount() > 0) {
   640→        $updateSql = "UPDATE users SET total_points = total_points + :score WHERE id = :user_id";
   641→        $updateStmt = $pdo->prepare($updateSql);
   642→        $updateStmt->execute([':score' => $total_score, ':user_id' => $user_id]);
   643→        if ($updateStmt->rowCount() === 0) { $pdo->rollBack(); return false; }
   644→    }
   645→    $pdo->commit();
   646→    return true;
   647→}
   648→```
   649→
   650→### Key behavior
   651→- Inserts into `trainings` with derived columns `total_score` (= correct_count) and `average_score` (accuracy %).
   652→- **Atomically** increments `users.total_points` by `total_score` inside the same transaction. If the points update fails (zero rows affected), the entire insert is rolled back.
   653→- Note: `UPDATE ... total_points = total_points + N` returns `rowCount()=0` if the user already has the same `total_points` value (i.e., when adding 0). This means saving a session where **0 questions were answered correctly** will silently roll back the whole transaction — a latent bug. The legacy comment even mentions logging "Failed to update total_points".

   809→## 17. Security issues / bugs / smells
   810→
   811→### Critical (integrity/abuse)
   812→1. **`saveTrainingResults` trusts client-supplied `isCorrect`**. A student can POST `results_json = [{question:"1+1", userAnswer:2, correctAnswer:2, isCorrect:true, timeTaken:0.01}, ...]` with `isCorrect:true` on every row to gain unlimited `total_points` and top the leaderboard. No server-side recomputation. The Next.js rebuild MUST re-derive correctness server-side from the questions and the user's answers.
   813→2. **No CSRF protection on any game-save POST** (`addition_subtraction_game.php`, `multiplication_game.php`, `division_game.php`, and the exam `save_exam` POST). An attacker site could trick a logged-in user into submitting fake results.
   814→3. **No rate limiting** on the save endpoints — trivial to spam POST requests to farm points.
   815→4. **`exam/generate-exam.php` save_exam** validates the JSON minimally (just `json_last_error() === JSON_ERROR_NONE && !empty($data)`). A malicious user could store arbitrary huge `settings_json` payloads (only constrained by MySQL `max_allowed_packet`).
   816→5. **`admin_statistics.php` `showDetails()`** inlines raw JSON into an HTML attribute via `htmlspecialchars($t['results_json'])` inside `onclick="showDetails(<?= htmlspecialchars($t['results_json']) ?>)"`. While `htmlspecialchars` escapes quotes, the JSON itself can contain crafted payloads that break out if quotes are not all escaped properly — should pass `JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_QUOT | JSON_HEX_APOS` instead.
   817→
   818→### Path / include bugs
   819→6. **`admin_statistics.php` line 2**: `include 'config.php';` and line 21 `header('Location: login.php');` — both should be `../config.php` and `../login.php` because the file lives in `/trainings/`. As-is, the file errors out. (Other admin files like `manage_user_stats.php` correctly use `../config.php`.)
   820→7. **`generate-exam.php` line 14**: `require_once '../config.php';` — but the file is at `/htdocs/exam/generate-exam.php`, so the path should be `../config.php` ✓ (correct).
   821→8. **`admin_statistics.php` chart only labels** `'جمع/طرح'` and `'ضرب'` — division is silently dropped from the doughnut.
   822→9. **`manage_user_stats.php` table** labels game types as either `'الضرب'` or `'الجمع والطرح'` — division and abacus render as the fallback label.
   823→10. **`statistics.php` "best game"** logic only filters by count, but for the `bar_comparison` chart it computes `div_perf` even when no division trainings exist (returns 0 %, which would tie for "best" if all games were unplayed).
   824→
   825→### SQL / query issues
   826→11. **`admin_statistics.php`** uses `LIMIT $limit OFFSET $offset` with string interpolation. Both values are sanitised to int, but the pattern is fragile; bound parameters are better.
   827→12. **`get_leaderboard.php`** uses MySQL-specific user variables `@rownum` and `SET @rownum = 0;` per request — works but isn't portable; in Supabase/Postgres, use `ROW_NUMBER() OVER (ORDER BY total_points DESC)`.
   828→13. **`generate-exam.php` POST** uses `header('Content-Type: application/json')` for the response but the request body is JSON (`php://input`); the route branches on `$_SERVER['HTTP_X_ACTION'] === 'save_exam'` — works, but using a custom HTTP header for routing is unusual and brittle.
   829→
   830→### Code smells
   831→14. **`saveTrainingResults` rollback** when `UPDATE ... total_points = total_points + 0` returns `rowCount()=0` (zero correct answers) — silently drops the training insert. Subtle bug; should commit regardless of whether the points update touches the row.
   832→15. **`exam-generator.php`** uses `FILTER_SANITIZE_STRING` which is **deprecated in PHP 8.1+**.
   833→16. **`exam-generator.php`** uses `srand((int)$seed)` for reproducibility — `rand()` is not cryptographically secure and seeded only the global RNG, not per-thread.
   834→17. **`generate-exam.php` JS** uses `Math.random()` for question generation — fine for an exam (not security-sensitive), but the file is **named "AI generator"** in the UI copy. No actual AI integration; consider replacing with the z-ai-web-dev-sdk LLM for narrative word-problem variants or adaptive difficulty.
   835→18. **Display-time bypass**: setup pages enforce `displayTime ∈ [0.1, 10]` seconds, but the game pages accept any `$_GET['displayTime']` value — a user can craft URLs with `displayTime=99999` to freeze the game or `displayTime=0` to break the flash logic. Server-side validation is missing.
   836→19. **`numberLength` and `termsCount` are not validated on the game pages** — URL can pass `numberLength=10` (would generate numbers up to 10^10) or `termsCount=1000`, both of which can DoS the browser.
   837→20. **`abacus_game.php` does not persist** any session data — there's no abacus row in `trainings`, so abacus is invisible in statistics/leaderboard. The Next.js rebuild should decide whether to persist abacus attempts.
   838→21. **`solvingMethod` is captured but unused** in add/sub, multiplication, and division games (the JS `generateQuestion` ignores it). Only the legacy `exam-generator.php` honors `friends_5` / `friends_10`.
   839→22. **No HTTPS enforcement** on the legacy host (`sql310.infinityfree.com`), and DB credentials are hardcoded in `config.php` — these will obviously change in the Supabase migration.
   840→23. **`updateExpiredAccounts()` and `deductDailyPoints()`** are run on every config.php include (every page load) — adds DB overhead per request. Supabase can move these into a scheduled Edge Function / cron.
   841→24. **Hardcoded CDN dependencies** (Tailwind, SweetAlert2, jsPDF, html2canvas, Chart.js, Bootstrap, FontAwesome) — must be replaced with proper npm packages in the Next.js rebuild.

   914→### 1.1 `notifications/FcmHandler.php` (119 lines)
   915→
   916→**Purpose.** A small from-scratch Firebase Cloud Messaging HTTP v1 sender. No SDK dependency — implements OAuth2 JWT bearer assertion manually with OpenSSL.
   917→
   918→**Constructor.**
   919→```php
   920→public function __construct($jsonFilePath)
   921→```
   922→Reads the JSON service-account file, sets `$this->serviceAccount` and `$this->projectId = $serviceAccount['project_id']`.
   923→
   924→**Private `getAccessToken()`.**
   925→- Builds a JWT with header `{alg:RS256, typ:JWT}` and claim:
   926→  - `iss` = serviceAccount `client_email`
   927→  - `scope` = `https://www.googleapis.com/auth/firebase.messaging`
   928→  - `aud` = `https://oauth2.googleapis.com/token`
   929→  - `iat` = now, `exp` = now + 3600
   930→- Signs with `openssl_sign(...SHA256)` using the service account `private_key`.
   931→- POSTs `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer&assertion=<jwt>` to `https://oauth2.googleapis.com/token`.
   932→- Returns `$data['access_token']`.
   933→
   934→**Public `sendNotification($deviceTokens, $title, $body, $data = [])`.**
   935→- Acquires access token; throws on failure.
   936→- URL: `https://fcm.googleapis.com/v1/projects/{$projectId}/messages:send`.
   937→- Headers: `Authorization: Bearer <token>`, `Content-Type: application/json`.
   938→- Builds a `targetLink` (hardcoded to `/notifications/user_notifications.php` on the current host — derived from `$_SERVER['HTTPS']` / `SERVER_PORT` / `HTTP_HOST`).
   939→- Normalises `$deviceTokens` to array, loops, POSTs per-token:
   940→```php
   941→$payload = [
   942→  'message' => [
   943→    'token'      => $token,
   944→    'notification'=> ['title' => $title, 'body' => $body],
   945→    'webpush'    => ['fcm_options' => ['link' => $targetLink]],
   946→    'data'       => array_merge($data, ['click_action' => 'FLUTTER_NOTIFICATION_CLICK']),
   947→  ],
   948→];
   949→```
   950→- Returns `["ok" => true, "results" => [...]]`.
   951→
   952→**Endpoints / actions.** None — it is a class.
   953→
   954→**DB tables.** None directly.
   955→
   956→**Notes / smells.**
   957→- `click_action = FLUTTER_NOTIFICATION_CLICK` is a Flutter-specific constant — copy-pasted from a Flutter project; irrelevant for web push. The SW never reads `click_action`.
   958→- `$targetLink` is built from `$_SERVER['HTTP_HOST']` without validation — open to Host header injection.
   959→- No batching: one HTTP request per token. Will not scale for thousands of users.

  1388→## 3. Notifications Flow (End-to-End)
  1389→
  1390→### 3.1 Token registration
  1391→
  1392→1. Student opens `dashboard.php` → clicks bell icon → goes to `notifications/user_notifications.php`.
  1393→2. Page loads Firebase compat SDK + the hardcoded `firebaseConfig` (projectId `notifications-b4b70`).
  1394→3. Student clicks "تفعيل التنبيهات" → `Notification.requestPermission()`.
  1395→4. On grant, `messaging.getToken({vapidKey: 'BKnyif...'})` registers a service worker (`/firebase-messaging-sw.js`) and obtains an FCM registration token.
  1396→5. JS POSTs `{token}` to `save_token.php`.
  1397→6. Server runs `UPDATE users SET device_token = ? WHERE id = ?` (overwriting any prior token — single-device model).
  1398→7. The same `device_token` column is **also** used by `config.php` for the device-cookie session binding. This means the FCM registration token and the session device cookie are stored in the same column → a freshly issued FCM token overwrites the device cookie and effectively logs the user out on next page load (since `hash_equals($user['device_token'], $currentToken)` will fail). **This is a latent bug**: the FCM token is a long base64-url string, not 64 hex chars; the device-cookie regex `^[a-f0-9]{64}$` would never match it, so the saved FCM token will fail validation and force logout on the next request.
  1399→
  1400→### 3.2 Admin sends notification
  1401→
  1402→1. Admin opens `notifications/admin_notifications.php`.
  1403→2. Fills title, picks `send_type` (broadcast|user), selects target user (or skips), writes rich HTML in Summernote.
  1404→3. POST `action=create` → INSERT row in `notifications`.
  1405→4. Server globs `__DIR__ . '/*.json'` to find the Firebase service-account JSON → instantiates `FcmHandler`.
  1406→5. Queries tokens:
  1407→   - broadcast: `SELECT device_token FROM users WHERE device_token IS NOT NULL AND device_token != ''`
  1408→   - specific: `SELECT device_token FROM users WHERE id = ? AND device_token IS NOT NULL AND device_token != ''`
  1409→6. Calls `$fcm->sendNotification($tokens, $title, $plain_body)` where `$plain_body = mb_strimwidth(strip_tags($msg), 0, 100, '...')`.
  1410→7. `FcmHandler` mints an OAuth2 access token (JWT signed with the service-account private key, exchanged at `oauth2.googleapis.com/token`), then POSTs per-token to `https://fcm.googleapis.com/v1/projects/notifications-b4b70/messages:send` with payload:
  1411→```json
  1412→{
  1413→  "message": {
  1414→    "token": "<device_token>",
  1415→    "notification": { "title": "...", "body": "..." },
  1416→    "webpush": { "fcm_options": { "link": "https://<host>/notifications/user_notifications.php" } },
  1417→    "data": { "click_action": "FLUTTER_NOTIFICATION_CLICK" }
  1418→  }
  1419→}
  1420→```
  1421→
  1422→### 3.3 Client receives
  1423→
  1424→- **Foreground** (`user_notifications.php` is open): `messaging.onMessage(payload)` fires → SweetAlert2 toast (top-end, 4s, pause on hover) + `updateBadgeCount()`.
  1425→- **Background / page closed**: `firebase-messaging-sw.js` `onBackgroundMessage` fires → `self.registration.showNotification(title, {body, icon:'/icon.png'})`. Click behaviour relies on the browser default (which uses `webpush.fcm_options.link` to focus/navigate the tab).
  1426→- **Polling backup**: `user_notifications.php` exposes `action=check_new` returning the latest unread row. The page itself doesn't poll in the visible JS, but the endpoint exists for future polling fallback (the comment in source says "طريقة احتياطية").
  1427→
  1428→### 3.4 Read state
  1429→
  1430→- Per-notification: `INSERT IGNORE INTO notification_reads (notification_id, user_id) VALUES (?, ?)`.
  1431→- Mark-all: SELECT all visible ids, then loop INSERT IGNORE per id (N+1).
  1432→- Unread count displayed in dashboard's bell badge via:
  1433→```sql
  1434→SELECT COUNT(*) FROM notifications n
  1435→LEFT JOIN notification_reads r ON n.id = r.notification_id AND r.user_id = ?
  1436→WHERE (n.is_broadcast = 1 OR n.user_id = ?) AND r.id IS NULL
  1437→```
  1438→
  1439→### 3.5 Topics
  1440→
  1441→No FCM topics are used. All targeting is by single-device token. Broadcast = loop over all tokens.

  1445→## 4. Auth & Session Lifecycle (Full)
  1446→
  1447→### 4.1 Registration
  1448→
  1449→1. Student fills 4-step wizard at `register.php`.
  1450→2. Email OTP: `send_reg_otp` generates `rand(1000,9999)`, stores in `$_SESSION['reg_otp']`, sends via raw SMTP socket to Gmail (`ssl://smtp.gmail.com:465`, `AUTH LOGIN`, base64 user/pass).
  1451→3. `verify_otp` does loose `==` comparison (type-juggling risk if either side becomes a non-numeric string).
  1452→4. Final POST: validates all fields, bcrypts password, **also stores `plain_password` plaintext**, sets `validity_end = now + 1 month`, INSERTs with status defaulting to `'pending'` (column default; not explicitly set).
  1453→5. Admin later approves (in `admin_panel.php`) → `status = 'approved'`.
  1454→
  1455→### 4.2 Login (cross-ref from `login.php`)
  1456→
  1457→1. User submits username + password.
  1458→2. `SELECT * FROM users WHERE username = ?`.
  1459→3. `password_verify($password, $user['password_hash'])`.
  1460→4. If `validity_end <= now`: `UPDATE users SET status = 'expired' WHERE id = ?`, deny login.
  1461→5. On success: `UPDATE users SET device_token = ?, session_ip = ?, session_agent = ? WHERE id = ?` (or the partial variant if device cookie was unchanged).
  1462→6. Sets `$_SESSION['user_id']`, `$_SESSION['is_admin']` (if admin), `$_SESSION['username']`.
  1463→7. Sets 1-year `device_token` cookie on the browser.
  1464→
  1465→### 4.3 Per-request session validation (config.php, runs on every page)
  1466→
  1467→For non-admin sessions:
  1468→- `SELECT device_token, status FROM users WHERE id = ?`.
  1469→- `$currentToken = deviceToken()` (reads cookie or generates+sets a new 64-hex cookie).
  1470→- If `!$user || empty($user['device_token']) || !hash_equals($user['device_token'], $currentToken) || $user['status'] !== 'approved'` → `session_destroy()` + redirect `login.php?reason=session_invalid`.
  1471→- Else `UPDATE users SET session_ip = ?, session_agent = ? WHERE id = ?`.
  1472→
  1473→This means: a single user is bound to a single device cookie. Logging in from a second browser overwrites `device_token` in DB → first browser's cookie no longer matches → next page load on first browser = forced logout. (Plus the FCM token overwriting issue noted in §3.1.)
  1474→
  1475→### 4.4 Auto-expiry
  1476→
  1477→Every page load: `UPDATE users SET status='expired' WHERE status='approved' AND validity_end <= NOW()`.
  1478→
  1479→### 4.5 Daily point deduction
  1480→
  1481→Every page load: `deductDailyPoints($pdo)` reads `system_settings.last_point_deduction`; if more than 86400s ago, runs `UPDATE users SET total_points = GREATEST(0, total_points - 3) WHERE status='approved' AND total_points > 0` and updates the timestamp. Effectively a -3/day decay on every approved user's `total_points`.
  1482→
  1483→### 4.6 Force logout (admin)
  1484→
  1485→In `admin_panel.php`: `UPDATE users SET session_ip = NULL, session_agent = NULL, device_token = NULL WHERE id = ?` → next page load by that user fails the `hash_equals` check → forced redirect to `login.php?reason=session_invalid`.
  1486→
  1487→### 4.7 Voluntary logout
  1488→
  1489→`logout.php`: clears `device_token` in DB (non-admins), clears both cookies, destroys session, redirects to `login.php?logged_out=1`.

  1493→## 5. Trainer Model
  1494→
  1495→- A **trainer** is a contact-record entity, NOT a login account. Fields: `id`, `name`, `phone` (11-digit Egyptian mobile, unique).
  1496→- Created/edited/deleted by admins only, via `trainers-dashboard.php`.
  1497→- Students reference their trainer via `users.trainer_id` (NULLABLE FK).
  1498→- Deleting a trainer nullifies `trainer_id` on all their students (transactional cascade-nullify), then deletes the trainer row.
  1499→- Admin can: assign single student to trainer, bulk-assign many students to one trainer, unassign a student, change student's `level` (1-10).
  1500→- Trainers themselves have no dashboard, no login, no permissions — they are pure data. The file name "trainers-dashboard.php" is misleading; it's the admin's trainer-management UI.
  1501→- Student-facing dashboard shows the student's `trainer_name` (LEFT JOIN to `trainers.name`) in the sidebar.
  1502→
  1503→**Implication for the new Supabase schema:** we should keep `trainers` as a separate table with RLS that only admins can write. Optionally we could promote trainers to authenticated users (Supabase auth.users) with a `role='trainer'` flag, but the legacy design does not require trainers to log in.

  1630→## 7. Security Issues, Bugs, and Smells
  1631→
  1632→### 7.1 Critical
  1633→
  1634→1. **Plaintext password column** (`users.plain_password`) — `register.php` INSERT and `admin_panel.php` UPDATE both write the raw password alongside the bcrypt hash. Anyone with read access to the DB has every user's password.
  1635→2. **Firebase service-account JSON committed to repo** — contains a real RSA-2048 private key (`notifications-b4b70-firebase-adminsdk-fbsvc-5be45cf153.json`). Must be rotated, removed from history, and moved to env secrets.
  1636→3. **Gmail SMTP App Password in source** — `register.php` hardcodes `SMTP_PASS = 'smuk abix frsf upow'`. Anyone with the source can send email as `baherbotros2003@gmail.com`.
  1637→4. **Hardcoded DB credentials in config.php** — `host=sql310.infinityfree.com`, `user=if0_39953844`, `password=IN24Uazap12`, `dbname=if0_39953844_login_system`. Committed to repo.
  1638→5. **`device_token` column is overloaded** — stores both the session device-cookie (64-hex regex `^[a-f0-9]{64}$`) and the FCM registration token (long base64-url). Saving an FCM token (≈200+ chars, not hex) breaks the session validation in `config.php` on the next page load → forces logout. **Likely a live bug** that may have been masked because most users never click "تفعيل التنبيهات".
  1639→
  1640→### 7.2 High
  1641→
  1642→6. **`verify_otp` uses loose comparison** (`$user_code == $session_code`) — PHP type juggling risk if `$session_code` ever becomes a non-string.
  1643→7. **No CSRF protection** on `save_token.php`, `check_new`, `get_message`, `mark_read`, `mark_all_read` (user_notifications.php) — only `send_notification` in user_notifications.php is "admin-only" guarded.
  1644→8. **Raw HTML stored in notifications.message** (admin_notifications.php via Summernote) — rendered with `innerHTML` on the read side → stored XSS. The in-page `user_notifications.php` send path uses `nl2br(htmlspecialchars())` so it's safe, but the admin path is not.
  1645→9. **`device_token` cookie is `HttpOnly` + `SameSite=Lax` + 1-year expiry** — fine, but it acts as a "remember-me" credential. If stolen (e.g. via XSS), the attacker can hijack the session from a different IP (no IP binding beyond `session_ip` info-only column).
  1646→10. **DB error messages returned verbatim** in `save_token.php` (`'DB Error: ' . $e->getMessage()`).
  1647→11. **`admin_notifications.php` `delete_all` truncates the notifications table** with only a JS `confirm()` — no soft-delete, no audit.
  1648→12. **No rate-limit on `send_reg_otp`** — attacker can spam OTPs and exhaust the Gmail account's daily quota.
  1649→13. **`FcmHandler` constructs target link from `$_SERVER['HTTP_HOST']`** without validation — Host-header-injection can craft phishing push notifications pointing to an attacker site.
  1650→
  1651→### 7.3 Medium
  1652→
  1653→14. **`mark_all_read` does N+1 INSERTs** instead of one batched multi-row insert.
  1654→15. **`lobby.php` calls `pvp_api.php`** which does not exist in the htdocs root (the real file is `pvp/challenge_api.php`). Either the file was deleted from this snapshot or the legacy host had a symlink/rewrite — broken in current state.
  1655→16. **Inconsistent sidebar direction** — student dashboard sidebar opens from LEFT (`-translate-x-full`), admin sidebar opens from RIGHT (`translateX(100%)`). Should be unified for RTL (open from RIGHT, i.e. `translate-x-full` initial).
  1656→17. **Inconsistent theme-toggle mechanism** — `body.light-mode` class vs `[data-theme="light"]` attribute.
  1657→18. **`click_action = 'FLUTTER_NOTIFICATION_CLICK'`** in FcmHandler is a Flutter-ism; the web SW never reads it.
  1658→19. **`FcmHandler::sendNotification` is sequential** (per-token cURL in a loop) — no batch send, no parallelism; will be slow with thousands of users.
  1659→20. **`updateExpiredAccounts` and `deductDailyPoints` run on every page load** — adds 2 writes to every request; should be a cron.
  1660→21. **Loose `==` in `verify_otp`** — type juggling risk.
  1661→22. **`register.php` `$_SESSION['reg_otp']` persists** until successful final POST — an attacker who knows the OTP can re-use it for arbitrary emails within the session TTL.
  1662→23. **`division.php` is on Bootstrap 5.3.3** with a totally different (green light) theme — inconsistent with the rest of the app's glass-morphism dark theme.
  1663→24. **`admin_notifications.php` uses `glob(__DIR__ . '/*.json')`** to find the service account — picks any random JSON in the folder; if more than one exists, behaviour is undefined.
  1664→25. **Admin's `device_token` is never cleared on logout** (asymmetric with students) — admins keep receiving pushes after logout.
  1665→26. **`notifications-b4b70-...json` filename contains the project name** — leaks identifier even without opening the file.
  1666→27. **No index hint** — `notification_reads` JOIN uses `(notification_id, user_id)` but the schema is not visible; if the UNIQUE is on `user_id` only (unlikely), queries would be slow.
  1667→
  1668→### 7.4 Low / cosmetic
  1669→
  1670→28. Background animation re-creates 15-20 DOM spans on every theme toggle — minor perf hit.
  1671→29. Tailwind CDN prints a console warning in production.
  1672→30. `division.php` mixes Bootstrap classes with inline-styled CSS variables — hard to maintain.
  1673→31. `trainers-dashboard.php` uses `Swal.fire` for both flash success/error and confirmations — overuse of toasts.
  1674→32. `lobby.php` mixes emoji-based "online" indicators (`.online-dot` green) with no real presence channel — purely relies on `last_activity > NOW() - 15s` polling.
  1675→33. `register.php` password suggestion generator uses `Math.random()` — not cryptographically secure (acceptable for client-side suggestions but worth noting).

  1679→## 8. Implications for the Next.js + Supabase Rebuild
  1680→
  1681→### 8.1 Schema (Supabase / Postgres)
  1682→
  1683→- `users` table: keep all columns EXCEPT `plain_password` (drop entirely) and probably `device_token` (split into `fcm_token TEXT` + `device_cookie_hash TEXT` to avoid the overload bug). Add `created_at TIMESTAMPTZ DEFAULT NOW()`, `updated_at TIMESTAMPTZ`.
  1684→- `trainers` table: keep as-is. Consider adding `email` so trainers could optionally log in in the future.
  1685→- `notifications` / `notification_reads`: keep; use a Postgres UNIQUE constraint on `(notification_id, user_id)` to make `INSERT ON CONFLICT DO NOTHING` work cleanly.
  1686→- `system_settings`: keep; one-row-per-key.
  1687→- Move auth to Supabase Auth (email + password; OTP via Supabase's built-in email templates → eliminates the SMTP-in-source problem).
  1688→- Move FCM token storage to a separate `user_fcm_tokens` table (one user → many devices) so multi-device support works.
  1689→
  1690→### 8.2 API routes (Next.js App Router)
  1691→
  1692→- `POST /api/notifications/save-token` → writes `user_fcm_tokens`.
  1693→- `POST /api/notifications/check-new` → returns latest unread.
  1694→- `POST /api/notifications/get-message` → single notification.
  1695→- `POST /api/notifications/mark-read` / `mark-all-read`.

  1851→### 1.4 Business logic
  1852→
  1853→**System settings (`getGameConfigs`)** — merges a hard-coded default array with DB rows from `system_settings`, so missing keys always fall back.
  1854→
  1855→**Challenge creation (`sendInvite`)**:
  1856→1. Look up tier config; if `tier{N}_status == 0` → reject with `tier{N}_msg`.
  1857→2. Verify sender has `pvp_points >= tier.loss` (i.e. the bet/loss-amount).
  1858→3. Verify target's `current_status !== 'playing'`.
  1859→4. Generate questions via `MentalMathGenerator::generateBatch($userLevel, $qCount)`.
  1860→5. Wrap questions with `config => {tier, duration: time*60, win_points, loss_points}` and store the whole thing as `questions_json`.
  1861→6. `BEGIN` → `UPDATE users SET pvp_points = pvp_points - loss WHERE id = sender` → `INSERT INTO pvp_matches (... 'pending' ...)` → `COMMIT`. Returns `match_id`.
  1862→
  1863→**Challenge timeout / accept (`respondToInvite`)**:
  1864→- On reject → refund sender (`pvp_points + bet_amount`), set status `'rejected'`.
  1865→- On accept → re-check invitee's `pvp_points >= bet_amount`; if not, refund sender and set status `'cancelled'`. Otherwise deduct from invitee, mark both users `'playing'`, set match status `'active'`, refresh `created_at = NOW()`.
  1866→- `checkMatchStatus` polls the match; if status still `'pending'` and `(time - strtotime(created_at)) > 30` seconds (this is the actual lobby-level timeout, **30s**), refund sender and mark `'cancelled'`.
  1867→
  1868→**Game flow (`submitScore` + `syncGameState` + `finishGameLogic`)**:
  1869→- `submitScore` dynamically picks `p1_score`/`p2_score`/`p1_progress`/`p2_progress`/`p1_status`/`p2_status` columns based on `userId == player1_id`. If `finished=true`, sets that player's `*_status='finished'`.
  1870→- `syncGameState` is polled by both clients every 1s. If both `*_status == 'finished'` and status != `'completed'`, runs `finishGameLogic` and tells client `check_result`.
  1871→- `finishGameLogic`:
  1872→  - Winner = higher score; tie → `winner_id = NULL`.
  1873→  - Reads `config` from `questions_json`; if missing, falls back to `{win_points: bet_amount, loss_points: bet_amount}`.
  1874→  - If winner: winner receives `win_points + loss_points` (i.e. the full pot, since each side wagered `loss_points`).
  1875→  - If draw: each side gets back `loss_points` (effectively a refund).
  1876→  - Sets both users `current_status = 'idle'`, sets match `status = 'completed', winner_id = ?`.
  1877→
  1878→**Surrender (`surrenderGame`)**:
  1879→- If `matchId` starts with `'AI_'` → log to `trainings` with `performance_notes='surrender'` and clear PHP session keys.
  1880→- Otherwise: fetch the match (must be `'active'`); winner = the other player; award `win_points + loss_points` to winner; mark match `'completed'`.
  1881→
  1882→**Daily bonus (`claimDailyBonus`)**: rand(50,60) points added if `last_daily_bonus != today`. Sets `last_daily_bonus = today`.
  1883→
  1884→**AI game flow**:
  1885→- `startAiGame` — respects `ai_status`, daily limit (`ai_attempts_count`, `ai_last_date`). Generates 100 questions; stores the answer key in **PHP session** under `ai_game_answers_{matchId}` and an empty user-answers map. Returns questions WITHOUT answers to the client. Bot speed (`min`/`max` ms per answer) scales by user level (lvl1: 2140–4280 ms; lvl4+: 1200–3000 ms). Match config: 7 minutes, win 50, loss 0.
  1886→- `storeAiAnswer` — persists each user answer to the PHP session map (per `q_index`).
  1887→- `submitAiScore` — server computes correctness from the session answer key (client-supplied `ai_score`, `ai_time`, `user_time` are believed for tie-break only). Win = user correct > AI correct; or equal correct AND `user_time < ai_time`. Award 50 to user on win, 0 otherwise; always set `current_status='idle'`; log to `trainings`.
  1888→
  1889→**Question generator (`MentalMathGenerator`)** — pure-PHP, abacus-style. Builds vertical stacked addition/subtraction problems with multi-digit operands, where each row's digit movement must obey rules allowed for the level:
  1890→- L1: `DIRECT` only
  1891→- L2: `DIRECT, COMP5`
  1892→- L3: `DIRECT, COMP5, COMP10`
  1893→- L4: digit-0 `DIRECT, COMP5`; digit-1 `DIRECT` only
  1894→- L5: `DIRECT, COMP5`
  1895→- Default: `DIRECT, COMP5, COMP10`
  1896→
  1897→Digits are 1–9, rows 3–5/6, numCols 1–2, opCols 1–2. Each question returned as `{q: "stacked text with +n / -n lines", a: integer}`.

  1905→### 1.7 Security / bugs / smells
  1906→- **SQL injection vector (mitigated but smelly)** in `submitScore`: column names (`p1_score`/`p2_score`/etc.) are interpolated into the SQL string via PHP variables: `$sql = "UPDATE pvp_matches SET $colScore = ?, $colProgress = ?";`. The values come from comparing `$userId == $p1Id`, so the strings are constant — but this pattern is dangerous and easy to break.
  1907→- **Stale-session trust**: AI game answers and user answers are kept in PHP `$_SESSION` (not in DB). If the user's session cookie is lost or PHP reaps the session, the AI match can never be scored. No DB persistence at all for in-progress AI matches.
  1908→- **Client-supplied AI score**: `submitAiScore` uses `ai_score`, `ai_time`, `user_time` from the POST body for tie-break decisions — a malicious client can claim arbitrarily fast `user_time` and slow `ai_time` to win every tie.
  1909→- **No CSRF protection**: every state-changing POST is reachable with a form-auto-submit cross-site. `generateCSRF()` exists in `config.php` but is never called here.
  1910→- **Race conditions**:
  1911→  - `respondToInvite` re-checks balance inside a transaction but doesn't `SELECT ... FOR UPDATE` the user row — two concurrent accepts of different invites could double-spend.
  1912→  - `claimDailyBonus` reads `last_daily_bonus` then updates — two parallel calls in the same second could award twice.
  1913→  - Stuck-match cleanup at the top of the file isn't inside the per-request transaction; two concurrent requests could both refund the same stuck match.
  1914→- **Maintenance cron pollution**: heavy SQL on every API request (stuck-match scan + status sweep) — should be a real cron, not request-time work.
  1915→- **`pvp_points` can go negative** in any code path that subtracts without a transaction-time check (e.g. `respondToInvite` does check, but `sendInvite` checks then writes outside any locking).
  1916→- **Hard-coded `100` questions** for AI in `startAiGame` ignores the tier `q` config — silently inconsistent with PVP tiers.
  1917→- **`$_POST['target_id']` not validated** to be a real user id before insert (FK will catch it but error message would be raw PDO exception).
